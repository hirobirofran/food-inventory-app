# 依存パッケージの更新は、マイナー・パッチなら CI 通過でマージし、むやみに最新にしない

依存パッケージの更新（Dependabot の PR も、手動の更新も。npm と GitHub Actions の両方）を、どこまで確認してから入れるか、どの版を選ぶかを決めた。

1. **マイナー・パッチ更新は CI（lint・test・型チェック。ビルドは含まない）が通ればマージする。** 表示確認が要るのは、メジャー更新で、かつ成果物や実行時の挙動に影響するパッケージのときだけ。区分は package.json の dependencies / devDependencies ではなく、成果物・実行時に影響するかで決める（例: 影響するのは next、react、react-dom、googleapis、@google/genai、tailwindcss、@tailwindcss/postcss。CI で検出できる開発用ツールは eslint、eslint-config-next、typescript、vitest、jsdom、@testing-library/*、@types/*）。例に無い依存は同じ基準で判定する。例外は 2 つ。`@types/node` は CI では分からない実行時の差が出るので、実行環境の Node の版（`.nvmrc`）に合わせる（`.github/dependabot.yml` の ignore がその設定）。`tsx` は CI で動かない（`seed:demo` だけで使う）ので、メジャーは seed:demo を動かして確かめる。GitHub Actions の更新は成果物・実行時に影響しないので、メジャーでも CI 通過でマージする。1 本の PR にメジャーとマイナーが混ざるときはパッケージ単位で判定し、表示確認が要るメジャーが 1 つでも含まれる PR は表示確認する。表示確認はオーナーが行い、デモのプレビューで画面を開く（`docs/SETUP.md`。本番用プレビューは確認に使わない）。Claude Code は代わりに行わず、結果を PR のコメントに記録する。理由: マイナー・パッチは互換性が保たれる前提で問題がほぼ出ず、確認を必須にすると更新が滞る。メジャーは CI が通っても実機で動かないことがあり、CI にビルドが無いので見た目の崩れは CI では分からない
2. **むやみに最新にしない。** 公開から 7 日未満の版は使わない（`.github/dependabot.yml` の cooldown と同じ趣旨。公開日は npm なら `npm view <pkg> time --json`、GitHub Actions なら GitHub のリリースで確かめる）。脆弱性の修正は、修正版のうち最小の版にする。Dependabot のセキュリティ更新 PR があればそれを使う。無いとき（開発用依存のアラートが自動で閉じられた、ignore 対象、修正版がメジャーのみ、など）も版の選び方は同じで、手動で上げるかどうかはオーナーが決める。修正版が公開 7 日未満でも、脆弱性の修正は入れる（Dependabot の cooldown も脆弱性修正の PR には効かない）。脆弱性の対象外のパッケージは、同じファミリーでも一緒に上げない。ただし、上げないと CI やインストールが通らない組（peer 依存など）は、必要な最小の版だけ一緒に上げてよい。理由を PR に書く。理由: 新しい版を入れること自体が供給網攻撃の入口になる（出典 3。オーナーが「今年 lint ツールの乗っ取りがあった」と指摘。事件の固有名は記録に無い）。開発時にしか使わないパッケージも例外ではない
