# Issue は起票時の要求として扱い、着手時に要件を定義してから実装する

Issue の本文は、起票時の要求である。
着手したら、最初に Issue を精査し、要件を定義する。
実装は、オーナーが要件定義に ok してから始める。

1. **Issue の本文は要求として扱う。**
   起票時には、要件定義はできていない。
   本文のどの欄（何が起きたのか、起票者の考察、完了条件、その他特記事項）も、見直しの対象にする。
   ただし、オーナーの決定は守る。
   オーナーの決定として扱うのは、次の 3 つだけ。
   - accepted の ADR
   - CLAUDE.md
   - オーナー自身が書いた Issue・PR のコメント（Claude Code の署名が無いもの）

   出典が、その点そのものを決めていることも確かめる。
   Issue 本文に ok をもらっても、本文の内容は決定にならない。
   Issue 本文は要求の置き場で、決まりの置き場ではないためである。
   Claude Code がまとめた決定の記録（#82 の決定のコメントなど）は、要件定義の案で「守る前提」として挙げる。
   その前提も、要件定義への ok で確かめる。
2. **着手時に、要件を定義する。**
   やることは次の 3 つ。
   - 目的を見直す（何のためか、何を守るか）
   - 要求を要件に整理する（満たすこと、制約、範囲外）
     - 設計を含むなら、責務の分け方と権限の境目も見る
   - 完了条件を決める

   要件定義は、Issue 本文との差分で書かない。
3. **要件定義は、オーナーの ok を得てから実装に入る。**
   要件定義の案は、チャットで見せる。
   案には、決め 2 の 3 つを見出しにして書く。
   当てはまるものが無い見出しには「なし」と書く。
   ok は、要件定義の案そのものにもらう。
   実装の指示や、成果物の案への ok は、要件定義の ok の代わりにしない。
   返事が無いことは、ok ではない。
   ok をもらったら、要件定義を Issue のコメントに残す。
   コメントには、ok の日時と場所（チャットのセッション ID など）を書く。
   本文の先頭には、要件定義のコメントへのリンクを足す。
   このリンクはコメントを残した後に決まるので、足すのに改めて ok は要らない。
   ok の後に要件を変えるときは、実装を止めて、同じ手順で ok を取り直す。
   作り直す Issue（完了を認められなかった Issue など）も、要件定義からやり直す。
   書き直した完了条件と合わなくなったチェックは外す。
4. **サブエージェントとレビューには、定義した要件を渡す。**
   Issue の文をそのまま指示に写さない。
   実装の指示とセルフレビューの要件には、定義した要件を渡す。
   PR 本文の「特にレビューしてほしい観点」に、要件定義のコメントへのリンクを書く。
   Codex を呼ぶコメントにも、同じリンクを書く。
   レビューの観点には「作りが目的と要件に合っているか」を入れる。
   要件定義で採った実現方法も、レビューで問い直してよいものとして渡す。
   「この設計を前提に」とは書かない。
5. **指摘を「決定済み」で退けるときは、出典のリンクを返信に書く。**
   出典にできるのは、決め 1 の 3 つだけ。
   要件定義で採った実現方法は、出典にしない。
   それを理由に退けたいときは、オーナーに諮る。
   指摘の一部だけを退けるときも同じ。
   出典が、指摘の点そのものを決めていることを確かめる。
   示せなければ、指摘を中身で判断し直す。
   指摘が決定や要件の前提を崩すときは、退けずにオーナーに諮る。
   出典のリンクは、CLAUDE.md の手順 2 の「理由」として書く。
   決定で退けるときは、行き先の Issue のリンクは要らない。

## 理由

#84 で、Claude Code は要件を定義せずに、Issue の本文どおりに実装した。
PR #112 のマージ後に、オーナーが問題を指摘した。

- Terraform の plan（変更の確認）と apply（適用）を、1 つのワークフローのファイルに入れた
  - この形は、#84 の完了条件に書かれていた
  - plan と apply は、責務も権限も違う
  - ファイルの先頭の設定（`permissions` と `env`）は、両方のジョブに効く
  - apply のために先頭へ設定を足すと、plan にも渡る作りだった
  - 2 つを分けるため、ジョブごとの大きな条件分岐（`if`）が要った
- plan と apply を、同じ concurrency のグループ（同時には 1 本しか走らせない組）に入れた
  - レビューは、承認待ちの apply が plan を止めるおそれがあると指摘した
  - Claude Code は、#82 で決めたことだとして、グループを分けなかった
  - 実際は、#84 の「起票者の考察」の欄に書かれた案だった
- 実装とセルフレビューの指示に、Issue の文をそのまま渡した
  - そのため、1 ファイルにした形を問うレビューは無かった

この ADR の Issue（#113）でも、同じ誤りを繰り返しかけた。

- 起票時の目的のまま ADR を書いた
- PR を作る指示と ADR の案への ok を、要件定義の代わりにした
- セルフレビューで、#84 の中心の誤りを防げないと指摘された
