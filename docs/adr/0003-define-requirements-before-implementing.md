# Issue は起票時の要求として扱い、着手時に要件を定義してから実装する

Issue の本文は、起票時の要求である。
着手したら、最初に Issue を精査し、要件を定義する。
実装は、オーナーが要件定義に ok してから始める。

1. **Issue の本文は要求として扱う。**
   起票時には、要件定義はできていない。
   目的、完了条件、起票者の考察のどれも、見直しの対象にする。
   ただし、オーナーの決定は守る。
   オーナーの決定は、出典で確かめられるものに限る。
   出典は、accepted の ADR、CLAUDE.md、決定と日付を書いた Issue・PR の本文かコメント。
   Issue 本文に ok をもらっても、本文の内容は決定にならない。
2. **着手時に、要件を定義する。**
   やることは次の 4 つ。
   - 目的を見直す（何のためか、何を守るか）
   - 要求を要件に整理する（満たすこと、制約、範囲外）
   - 完了条件を、要件に合わせて書き直す
   - 実現方法の案の採否を、要件から決める
   設計の案なら、責務の分け方と権限の境目も見る。
3. **要件定義は、オーナーの ok を得てから実装に入る。**
   要件定義の案を見せて、ok をもらう。
   ok をもらったら、Issue のコメントに記録する。
   完了条件を書き直すときは、Issue 本文も直す。
4. **サブエージェントには、定義した要件を渡す。**
   Issue の文をそのまま指示に写さない。
   実装の指示とセルフレビューの要件には、定義した要件を渡す。
   レビューの観点には「作りが目的と要件に合っているか」を入れる。
5. **指摘を「決定済み」で退けるときは、出典の URL を返信に書く。**
   出典が、指摘の点そのものを決めていることを確かめる。
   示せなければ、指摘を中身で判断し直す。
   指摘が決定や要件の前提を崩すときは、退けずにオーナーに諮る。

## 理由

#84 で、Claude Code は要件を定義せずに、Issue の本文どおりに実装した。
PR #112 のマージ後に、オーナーが問題を指摘した。

- Terraform の plan（変更の確認）と apply（適用）を、1 つのワークフローのファイルに入れた
  - この形は、#84 の完了条件に書かれていた
  - plan と apply は、責務も権限も違う
  - ファイルの先頭の設定（`permissions` と `env`）は、両方のジョブに効く
  - apply のために先頭へ設定を足すと、plan にも渡る作りだった
  - 2 つを分けるため、ジョブごとの大きな条件分岐（`if`）が要った
- plan と apply を、同じ concurrency のグループ（同時には 1 本しか走らせない組）に入れた
  - レビューは、承認待ちの apply が plan を止めると指摘した
  - Claude Code は「#82 の決定」として、グループを分けなかった
  - 実際は、#84 の「起票者の考察」の欄に書かれた案だった
- 実装とレビューの指示に、Issue の文をそのまま渡した
  - そのため、実装もレビューも「Issue に合っているか」を基準にした

この ADR の Issue（#113）でも、同じ誤りを繰り返しかけた。

- 起票時の目的のまま ADR を書いた
- セルフレビューで、#84 の中心の誤りを防げないと指摘された
