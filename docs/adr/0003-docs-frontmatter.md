# 人が読むために書いた文書には、audience・purpose・updated のフロントマターを付ける

人が読むために書いた文書の先頭に、フロントマター（ファイル先頭の `---` で囲んだ項目欄）を付けるかどうか、どの項目を書くか、どの文書に付けるかを決めた。

## 1. 項目は audience・purpose・updated の 3 つ

値は本文と同じ言語で書く（英語の `README.md` は英語で書く）。

### audience

- 書くこと: 想定読者（誰が読む想定か）と、前提知識（読むために必要な知識）。前提知識は、読む人によって持っているかどうかが分かれるものだけを書く。誰でも持っているもの（日本語が読める、など）と、その文書の中で説明しているものは書かない。先に読んでおくべき文書があれば、それを書く
- 例: `このアプリを Google Cloud と Vercel で動かす人。Git とターミナルを使える。`、`コードを直す開発者。Next.js と TypeScript を使ったことがあり、docs/ARCHITECTURE.md を読んでいる。`
- 理由: 前提知識がわかれば、書く人は何を説明し何を省くかを決められ、読む人は自分向けの文書かを判断できる。例と線引きが無いと、文書ごとに書く細かさがばらばらになる

### purpose

- 書くこと: 文書目的。なぜこの文書があるのか、読む人は何を得るのか、何を伝え何を残したいのか（WHY）を、一文で書く。「〜の手順です」のような内容の要約は書かない
- 使い方: 書く人にとっては、この文書が扱う範囲の宣言になる。文書を直すときは、範囲の外のことを書いていないかを確かめるのに使い、文章が膨らんだら、文書を分けることを考えるのに使う。読む人にとっては、自分向けの文書か、読んで何を得られるかを一文でつかむのに使う

### updated

- 書くこと: 本文を最後に変えた日付（日本時間）。本文を変えたら書き換える。フロントマターだけを変えたときは書き換えない
- 理由: git の履歴を見なくても、文書を開いただけでいつの内容かがわかる。更新は日付を書き換えるだけで手間がかからない
- 書き換え忘れを自動で確かめる仕組みは、今は作らない。理由: 自動の確認は、決まりを守れる状態ができてから入れる。このリポジトリでは、lint などの確認も、通る状態を先に作ってから条件にしている

### 使わない項目

- `title`: 題名は本文の見出し 1 に書く。フロントマターにも書くと、同じ題名を 2 か所で直すことになる
- `description`: 内容を説明する欄で、目的とは別のもの。目的は purpose に書く

## 2. 付けるのは、人が読むために書いた文書

- 今はルートの `README.md`、`docs/` の `VISION.md`・`ARCHITECTURE.md`・`SETUP.md`・`KNOWLEDGE.md`・`TASKS.md`、`docs/adr/README.md` の 7 本。人向けの文書を新しく作るときも付ける
- `README.md` も対象にする。理由: 外部の人は、まだ何も知らないときに README を読む。数行で想定読者と目的がわかると助かる。ルートの README は長くなりがちで、目的を先に書けば書きすぎを防げる

次の文書には付けない。

- エージェント向けの文書（`CLAUDE.md`、`AGENTS.md`、`docs/agents/`、`handoff/`）。理由: updated を付ける意味が無く、かえって害になる。人間が読まないので、目的を書いても活かされない。人間向けでないことは置き場所でわかる
- ADR の各ファイル。理由: status などの専用のフロントマターを持つ。決まったことは書き換えず、新しい ADR で置き換える
- `.github/` のテンプレート。理由: 先頭の項目欄は GitHub が読む設定欄
