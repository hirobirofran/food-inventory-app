# 人が読むために書いた文書には、title・audience・purpose・updated のフロントマターを付ける

人が読むために書いた文書の先頭に、フロントマター（ファイル先頭の `---` で囲んだ項目欄）を付けるかどうか、どの項目を書くか、どの文書に付けるかを決めた。

1. **項目は title・audience・purpose・updated の 4 つにし、description は使わない。**
   - `title`: 題名
   - `audience`: 想定読者。誰が読むかと、その人がすでに知っていること（前提知識）を書く
   - `purpose`: 文書目的。なぜこの文書があるのか、読む人は何を得るのか、何を伝え何を残したいのかを書く。「〜の手順です」のような内容の要約は書かない
   - `updated`: 本文を最後に変えた日付（日本時間）。本文を変えたら書き換える。フロントマターだけを変えたときは書き換えない。更新漏れを自動で確かめる仕組みは、今は作らない
   - 値は本文と同じ言語で書く。英語の `README.md` は英語で書く

   理由: purpose は、読む人にとってはこの文書の目的になり、書く人にとってはこの文書が扱う範囲の宣言になる。audience に前提知識まで書くと、書く人は何を説明し何を省くかを決められ、読む人は自分向けの文書かを判断できる。updated があれば、git の履歴を見なくても、文書を開いただけでいつの内容かがわかる。更新は日付を書き換えるだけで手間がかからない。description は内容を説明する欄で、目的とは別のものなので、purpose に置き換える

2. **付けるのは、人が読むために書いた文書。** 今はルートの `README.md`、`docs/` の `VISION.md`・`ARCHITECTURE.md`・`SETUP.md`・`KNOWLEDGE.md`・`TASKS.md`、`docs/adr/README.md` の 7 本。人向けの文書を新しく作るときも付ける。

   理由（README も対象にする）: 外部の人は、まだ何も知らないときに README を読む。数行で想定読者と目的がわかると助かる。ルートの README は長くなりがちで、目的を先に書けば書きすぎを防げる

   次の文書には付けない
   - エージェント向けの文書（`CLAUDE.md`、`AGENTS.md`、`docs/agents/`、`handoff/`）: updated を付ける意味が無く、かえって害になる。人間が読まないので、目的を書いても活かされない。人間向けでないことは置き場所でわかる
   - ADR の各ファイル: status などの専用のフロントマターを持つ。決まったことは書き換えず、新しい ADR で置き換える
   - `.github/` のテンプレート: 先頭の項目欄は GitHub が読む設定欄
