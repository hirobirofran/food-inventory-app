# Issue に書いた実現方法は起票時の案として扱い、着手時に目的から採否を決める

Issue の実現方法は、決まりではなく案として扱う。

1. **守るのは、ゴールとオーナーの決定だけ。**
   ゴールは、完了条件に書いた状態。
   オーナーの決定は、出典（コメントの URL）で示せるもの。
   それ以外の実現方法は、起票時の案とする。
   実現方法とは、ファイルの構成、仕組みの分け方、名前などのこと。
2. **着手時に、案を 1 つずつ目的から判断する。**
   実装者は、実現方法を「決定」と「案」に分ける。
   案は、目的から採否を決める。
   目的とは、守るもの、責務の分け方、権限の境目のこと。
   採否と理由は、PR 本文に書く。
3. **サブエージェントには、案を判断の対象として渡す。**
   実装の指示で「守ること」にするのは、ゴールと決定だけ。
   レビューの指示には「案そのものが目的に合っているか」を入れる。
4. **指摘を「決定済み」で退けるときは、出典を示す。**
   示せなければ、指摘を中身で判断し直す。

理由: #84 で、Issue の案をそのまま実装した。
plan と apply を 1 つのワークフローに入れた。
ファイルの先頭の設定は、両方のジョブに効く。
そのため、apply 用の設定が plan に渡る作りになった。
レビューの「グループを分けるべき」という指摘も、「#82 の決定」として退けた。
実際は、#84 本文の「起票者の考察」の案だった。
指示もレビューも「Issue に合っているか」だけを見ていた。
そのため、マージ後まで気づかなかった。
