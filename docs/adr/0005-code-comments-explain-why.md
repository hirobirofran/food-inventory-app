# コードのコメントには、処理の言い直しを書かず、なぜその処理なのかを書く

コードのコメントに何を書くかを決めた。処理の言い直しは書かない。なぜその処理なのかを書く。理由が無いなら、コメントを書かない。

## 1. 決まり

- コメントには、処理の言い直しを書かない。なぜその処理なのかを書く
- 理由が無いなら、コメントを書かない
- 対象は、これから書く・直すコメント。今あるコメントを一括では書き直さない

## 2. 理由

- コードを後から読む人（オーナー、後任のセッション、公開リポジトリの読者）は、その処理を消してよいか・変えてよいかを判断したい。それには理由が要る
- 処理の言い直しは、コードを読めば分かる。理由は、コードからは分からない
- 決まりが文書に無かったので、書く側もレビューする側も、この点を見なかった

## 3. 例

悪い例（処理の言い直し。なぜ plan し直すのかが分からない）:

    # apply の直前にもう一度 plan し、その要約を出してから、同じ plan をそのまま apply する

良い例（同じ箇所を書き直したもの。`.github/workflows/terraform-apply.yml`）:

    # 承認の後に plan し直すのは、PR の plan の結果ファイルが Terraform の値をすべて含み、公開リポジトリの成果物に残せず、持ち越せないため。

## 4. 守らせ方

- CLAUDE.md の「重要ルール」にこの決まりを置く。コードを書くエージェントが、毎セッション目にするため
- セルフレビュー、`/code-review`、Codex の 3 つには、回すたびに「コメントがこの決まりに合っているか」を観点として渡す。観点を渡さない `/code-review` はコメントの問題を 1 件も挙げず、観点を渡すと 9 件を挙げたため
- Codex には、呼ぶコメントの中で観点を渡す。AGENTS.md には書かない。呼ぶコメントで渡せば足り、AGENTS.md に書いて効いたかを確かめる方法が無いため
- `/simplify` には渡さない。役割は重複や簡素化の確認で、決まりの確認は上の 3 つで足りるため
