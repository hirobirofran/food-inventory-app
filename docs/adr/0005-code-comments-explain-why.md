# コードのコメントには、処理の言い直しを書かず、なぜその処理なのかを書く

コードのコメントに何を書くかを決めた。処理の言い直し（コードを読めば分かる、何をしているかの説明）は書かない。なぜその処理なのかを書く。理由が無いなら、コメントを書かない。

## 1. 決まり

- コメントには、処理の言い直しを書かない。なぜその処理なのかを書く
- 理由が無いなら、コメントを書かない
- 対象は、これから書く・直すコメント。今あるコメントを一括では書き直さない

## 2. 理由

- コードを読む人は、その処理を消してよいか・変えてよいかを判断したい。それには理由が要る。読む人には、リポジトリのオーナー、後から作業する Claude Code、公開リポジトリの読者がいる
- 処理の言い直しは、コードを読めば分かる。理由は、コードだけからは分からないことが多い
- PR #117（2026-11-23）の時点では、この決まりが文書に無かった。そのため、コードを書く人もレビューする人も、コメントに理由が書いてあるかを確かめていなかった（Issue #118）

## 3. 例

例は、Terraform（インフラの設定をコードで管理するツール）を GitHub Actions で動かすワークフローのコメント。plan は変更の内容を計算すること、apply はその変更を反映すること。

悪い例。処理の言い直しで、なぜ plan し直すのかが分からない。出どころはコミット 7e354a2 の `.github/workflows/terraform-apply.yml` の 138 行目:

    # apply の直前にもう一度 plan し、その要約を出してから、同じ plan をそのまま apply する

良い例。同じ箇所を書き直したもの。plan し直す理由と、plan の結果ファイルを apply に渡す理由を書いている。成果物（artifact）は、GitHub Actions の実行で保存して、後の実行に渡せるファイルのこと。出どころはコミット 68dc0d6 の同じファイルの 139〜141 行目:

    # 承認の後に plan し直すのは、PR の plan の結果ファイルが Terraform の値をすべて含み、公開リポジトリの成果物に残せず、持ち越せないため。
    # 結果ファイル（tfplan）を apply に渡すのは、ログに出した要約と反映する中身を一致させるため。
    # また、plan の後に state が変わっていたら、Terraform が反映せずに止まるため

## 4. コードを書く人とレビューする人への伝え方

- CLAUDE.md（Claude Code がセッションの始めに読む指示ファイル）の「重要ルール」に、この決まりを書く。コードを書く Claude Code が、毎回のセッションで読むため
- 次の 3 つのレビューを頼むたびに、CLAUDE.md の「コードレビューの手順」の節にある文を、依頼に書き添える
  - セルフレビュー: ドラフト PR を作る前のレビュー。Claude Code が `superpowers:requesting-code-review` のスキルで、サブエージェントに差分をレビューさせる。サブエージェントは、Claude Code が別に立ち上げるエージェント。スキルがサブエージェントに渡す依頼文に書き添える
  - `/code-review`: Claude Code のレビュー用のコマンド。コマンドの引数（`--comment` の後ろ）に書き添える
  - Codex: OpenAI のコーディングエージェント。PR のコメントで codex をメンションするとレビューする。そのコメントに書き添える
- 書き添えるのは、書き添えずに実行した `/code-review` が、コードのコメントの問題を 1 件も挙げなかったため。悪い例のコメントは、そのときの差分にもあった（コミット 5087a68 の同じファイルの 126 行目）。書き添えて実行した回では、コードのコメントの問題を 9 件挙げた（出典 2）
- 書き添える文の置き場は、CLAUDE.md の「コードレビューの手順」の節の 1 か所にする。スキル（Claude Code に読み込ませる手順書）や PR テンプレートには書かない。レビューの手順の説明はこの節にあり、PR テンプレートはその実施を確かめるチェックリストだけを持つため
- `docs/agents/domain.md` には「手順になったものはスキルにする」とある。この手順は、置き場を 1 か所にするため、その例外とする
- Codex に書き添える文は、AGENTS.md（Codex などのエージェントが読む指示ファイル）には書かない。呼ぶコメントに書けば足りるため。また、AGENTS.md に書いても、Codex がそれを観点にしてレビューしたかを、結果から見分ける方法が無いため
- `/simplify`（Claude Code の、コードの重複や簡素化を見つけて直すコマンド）には書き添えない。`/simplify` の役割はコードの重複や簡素化で、コメントの中身を確かめることではない。この決まりの確認は上の 3 つで足りる
