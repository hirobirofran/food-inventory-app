# コードのコメントには、処理の言い直しを書かず、なぜその処理なのかを書く

コードのコメントに何を書くかを決めた。処理の言い直し（コードを読めば分かる、何をしているかの説明）は書かない。なぜその処理なのかを書く。理由が無いなら、コメントを書かない。

## 1. 決まり

- コメントには、処理の言い直しを書かない。なぜその処理なのかを書く
- 理由が無いなら、コメントを書かない
- 対象は、これから書く・直すコメント。今あるコメントを一括では書き直さない

## 2. 理由

- コードを後から読む人は、その処理を消してよいか・変えてよいかを判断したい。それには理由が要る。読む人には、リポジトリのオーナー、後から作業する Claude Code、公開リポジトリの読者がいる
- 処理の言い直しは、コードを読めば分かる。理由は、コードからは分からない
- これまでは、この決まりが文書に無かった。そのため、コードを書く側もレビューする側も、コメントに理由が書いてあるかを確かめていなかった

## 3. 例

悪い例（処理の言い直し。なぜ plan し直すのかが分からない。コミット e4cb4d7 の `.github/workflows/terraform-apply.yml`）:

    # apply の直前にもう一度 plan し、その要約を出してから、同じ plan をそのまま apply する

良い例（同じ箇所を書き直したもの。コミット 68dc0d6 の同じファイル）:

    # 承認の後に plan し直すのは、PR の plan の結果ファイルが Terraform の値をすべて含み、公開リポジトリの成果物に残せず、持ち越せないため。

## 4. コードを書く人とレビューへの伝え方

- CLAUDE.md（Claude Code がセッションの始めに読む指示ファイル）の「重要ルール」に、この決まりを書く。コードを書く Claude Code が、毎回のセッションで読むため
- 次の 3 つのレビューを頼むたびに、「コードのコメントがこの決まりに合っているか」の確認を依頼に書き添える。書き添える文は、CLAUDE.md の「コードレビューの手順」の節にある
  - セルフレビュー: ドラフト PR を作る前に、Claude Code がサブエージェント（Claude Code が別に立ち上げるエージェント）に差分をレビューさせる。サブエージェントへの依頼文に書き添える
  - `/code-review`: Claude Code のレビュー用のコマンド。コマンドの後ろ（引数）に書き添える
  - Codex: OpenAI のコーディングエージェント。PR のコメントで呼ぶとレビューするので、呼ぶコメントに書き添える
- 書き添えるのは、書き添えないとコメントの問題が指摘されなかったため。`/code-review` は、書き添えなかった回ではコメントの問題を 1 件も挙げなかった。書き添えた回では 9 件を挙げた（出典 2）
- 書き添える手順は、CLAUDE.md の「コードレビューの手順」の節に書く。スキル（Claude Code に読み込ませる手順書）や PR テンプレートには書かない。レビューの手順はすでにこの節にあり、書く場所を 1 か所にするため
- `docs/agents/domain.md` には「手順になったものはスキルにする」とある。この手順は、上の理由でその例外とする
- Codex 向けの確認は、AGENTS.md（Codex などのエージェントが読む指示ファイル）には書かない。呼ぶコメントに書けば足りるうえ、AGENTS.md に書いても効いたかを確かめる方法が無いため
- `/simplify`（Claude Code の、コードの重複や簡素化を確かめるコマンド）には書き添えない。役割が違い、この決まりの確認は上の 3 つで足りるため
