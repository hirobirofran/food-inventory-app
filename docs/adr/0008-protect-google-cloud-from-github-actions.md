# GitHub Actions の想定外の操作から Google Cloud を守り、どのワークフローも外部の部品をコミット ID で固定する

GitHub Actions に、Terraform で Google Cloud を変える強い権限を渡す（#82）。
PR #91 で、自動のセキュリティ確認が、権限について指摘を出した。
指摘を 1 件ずつ見ても、直す価値があるかを判断できなかった。
そこで、何を誰から守るかを先に決めた。
指摘や対策は、これに照らして選ぶ。
この方針は基本方針で、実際と合わない所が出たら見直す。

## 守るもの

Google Cloud のプロジェクトの中身。
アプリが使うサービスアカウント（以下 SA）と、Terraform が作る物を指す。

理由: この中に、アプリのデータ（スプレッドシート）を読める SA がある。
乗っ取られると、データを読まれたり、アプリが動かなくなったりする。

## 守る相手

- A. 外部の人の PR
  - 公開リポジトリなので、誰でも PR を出せる。
  - ただし、オーナーがレビューで止められる。
    fork からの PR の自動処理には、Secrets が渡らない。
    そのため、ほぼ別扱いにする。
  - 例外は、他人の PR をきっかけに、強い権限でワークフローを動かす書き方（`pull_request_target`）。
    PR のコードを取り込むと、そのコードが強い権限で動く。
    **この書き方は使わない。**
- B. ワークフローが使う外部の部品（Actions、Terraform のプロバイダ）の乗っ取り
  - 2025 年に、広く使われていた Actions の部品（tj-actions/changed-files）が乗っ取られた。
    使っていたリポジトリの秘密が漏れた。
  - 自分では防げず、気付きにくい。
- C. 身内（Claude とオーナー）の誤り
  - 変更を入れるのは、Claude とオーナーだけ。
    いちばん起きやすいのは、悪意より誤り。

## 考えない範囲

- オーナー本人の GitHub・Google のアカウントの乗っ取り
  - 乗っ取られると、レビューも承認もオーナーとしてできてしまう。
    この仕組みの中では防げない。
  - アカウントは、2 段階認証などで別に守る。
- GitHub・Google そのものの乗っ取り
  - 自分たちでは手が出せない。

## 対策

1. **Terraform の apply（変更を実際に反映する操作）の前に、オーナーの承認を入れる。**
   - 承認できるのはオーナーだけ。
   - main へのマージで apply のジョブは自動で動き出し、オーナーの承認を待って止まる。
   - apply 用の SA を借りられる（その SA の権限で動ける）のは、承認を通ったジョブだけにする。
     main ブランチで動くだけでは借りられない。
   - 理由: 強い権限を使う直前に、必ずオーナーの目が入る。
     A・B・C のどれにも効く。
     apply はめったに無く、オーナーの目の前で行うので、承認の手間は小さい。
2. **権限は、#82 の子の Issue ごとに、必要な分だけ付ける。**
   - apply 用の SA にプロジェクト全体で付けた強い権限は、Terraform が扱う物が決まる #85 で見直す。
   - 理由: 誤り（C）で壊れる範囲を小さくするため。
     乗っ取りへの対策は 1 で行う。
3. **ワークフローの YAML が呼ぶ外部の部品（Actions）は、版の番号ではなくコミット ID で指す（固定する。版の番号はコメントで添える）。**
   - 対象は、すべてのワークフロー。
     Google Cloud の権限を使うワークフローに限らない。
   - 固定を壊す PR（部品をコミット ID 以外で指す PR）はマージしない。
   - Terraform のプロバイダの版の固定は、#90 で扱う。
   - 理由:
     - 版の番号は、作者が別の中身に付け替えられる（B）。
     - 固定は、2026 年に起きた部品の乗っ取りの事故を前提にしている。
       乗っ取られた部品は、どのワークフローで動いても害を出す。
     - 固定を壊せば、中身を差し替えられるリスクを許容することになる。
4. **Terraform の state（Terraform が管理している物の記録）とログを置くバケット、データを読む SA は、Terraform で消せないようにする。**
   - 理由: 誤った変更（C）で消えると、元に戻すのが難しい。
     特に state を失うと、Terraform は今ある物を把握できなくなる。

## そのほかの決め

- **リポジトリは、名前ではなく、GitHub がリポジトリごとに振る番号で見分ける。**
  - 対象: GitHub のジョブが Google Cloud に入るときの入口（Workload Identity Federation の設定）の条件
  - 対象: plan（Terraform が変更の予定を出す操作）用の SA を借りられる相手の指定
  - 理由: 名前は、このリポジトリの名前を変えたり消したりした後に、第三者が取り直せる。
    取り直したリポジトリからは、plan 用の SA（読むだけ）を借りられてしまう。
    番号は名前を変えても変わらず、他人が同じ番号を取ることもできない。
    Google の公式文書も、番号で見分けることを勧めている。
  - 起きる見込みは低い。
    ただ、入口を作っていた時点（#83）なら、直す手間が最も小さかった。
- **Claude が apply を承認できないようにする。**
  - Claude Code のプロジェクトの設定で、次の API を Claude が実行できないようにする。
  - 対象: 承認待ちのデプロイ（対策 1 で承認を待って止まった apply のジョブ）を承認・却下する GitHub の API
  - 対象: Environment（ジョブに承認などの条件を付ける GitHub の仕組み。対策 1 の承認に使う）を作る・変える・消す API
  - オーナーが画面で承認する流れは変わらない。
  - 理由: Claude Code は、オーナーと同じ GitHub CLI（gh）のログインで動く。
    Claude が誤ってこれらの API を呼ぶと、デプロイが承認されたり、承認する人が変わったりする。
    すると、オーナーが画面を見ないまま apply が進む。
    GitHub からは、オーナーの承認と区別がつかない。
    対策 1 が、身内の誤り（C）に効かなくなる。
  - これは誤りへの対策で、乗っ取りへの対策ではない（コマンドの書き方を変えれば、この設定をすり抜けられる）。
    オーナーのアカウントの乗っ取りは、「考えない範囲」に入る。
  - Claude 用に別の GitHub アカウントを作る案は、見送った。
    ログインとトークンの管理が増えるため。

## ADR-0001 との関係

[ADR-0001](0001-dependency-update-policy.md) は、依存パッケージ（npm と GitHub Actions）の更新を、どこまで確かめて入れるか、どの版を選ぶかを決めている。
この ADR は、そのうち GitHub Actions に、対策 3 の固定を足す。
固定を壊す PR は、ADR-0001 の条件を満たしていてもマージしない。
npm の依存は対象にしない。
