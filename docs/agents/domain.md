# ドメイン文書の読み方

このリポジトリで作業するエージェント全般（スキルを使うときも、使わないときも）の読み方。

## 調べる前に読む

- ルートの `GLOSSARY.md`
- `docs/adr/`: まず `README.md`（索引、1 件 1 行）を見て、いま触る領域に関わる ADR だけ読む

無いものは黙って飛ばす。無いことを指摘したり、先に作ろうと提案したりしない。用語や決定が実際に固まったときに `/domain-modeling` の書式で作る。ただし ADR と GLOSSARY を作る・変えるときは、本文の案を見せてオーナーの ok を得てから（2026-10-23 に許可なく作った ADR の PR #70 は却下された）。

## ADR の運用（このリポジトリの決め）

- `status` は必須。エージェントが書くときは `proposed`（まだ決まっていない、または提案）。`accepted`（決まった）にできるのはオーナーが明示的に決めたときだけで、出典にその日時を書く。見直したら `superseded by ADR-NNNN`、使わなくなったら `deprecated`
- 書く基準は 2 つのどちらか。`/domain-modeling` の ADR 形式の基準（元に戻しにくい、文脈なしでは意外、本物のトレードオフがある）がそろうとき。または、次のセッションが知らないと同じ確認や失敗を繰り返す決定（運用・手順の決めを含む。例: Dependabot のマイナー・パッチ更新は CI 通過でマージする）
- `handoff/ideas/` との使い分けは対象で分ける。ideas は「やりたいこと・調べたいこと」（記録だけのものも含む）、ADR は「決めた方針」（`proposed` も含む）。ideas の案を方針にして ADR へ移すときはオーナーの ok を得る
- ADR を作ったら `docs/adr/README.md` の索引に 1 行足す
- 毎セッション守らせることだけ、CLAUDE.md に 1 行で参照を足す。手順になったものはスキルにする。ADR には「なぜ」を残す
- 本文の後に `## 出典` 節を置き、日時と要旨を書く（例: 「2026-10-14 20:22Z、オーナー、Claude Code のチャット。マイナー更新は CI 通過でマージすると決定」）。このリポジトリは public なので、発言の原文は引用しない。本文の書式は `/domain-modeling` の ADR 形式

## 用語は GLOSSARY のとおりに使う

Issue の題名、提案、仮説、テスト名で、GLOSSARY が避けている同義語に流れない。無い用語が要るなら、作らずに記録して `/domain-modeling` に回す。
